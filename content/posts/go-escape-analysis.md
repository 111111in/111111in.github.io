写 Go 的人迟早都会遇到一个「反直觉」的现象：同样是打印一个变量，内置函数 `println(x)` 不会触发堆分配，而 `fmt.Println(x)` 却会让 `x` 逃逸到堆上。要真正看懂这背后的原因，就得理解 Go 里一个被严重低估的机制——**逃逸分析（Escape Analysis）**。

这篇文章不打算复述文档，而是从「内存到底放在哪」这个最根本的问题出发，配合可运行的代码和编译器输出，把逃逸分析讲透。

## 一、Go 内存的两块区域：栈与堆

Go 的内存分配分两个层次，理解它们的差异是理解逃逸分析的前提。

### 栈（Stack）

每个 goroutine 都有一块独立的栈，初始大小约 **2KB**（Go 1.13 之后），按需增长，64 位系统下最大可到约 1GB。栈上的分配极其廉价——编译器在编译期就能确定变量的大小和生命周期，函数调用时只需要**移动一下栈指针**，函数返回时整块栈帧随之销毁，无需任何 GC 介入。

代价是：栈上变量的生命周期被严格限制在**当前函数调用之内**。函数一返回，栈帧回收，里面的变量就不存在了。

### 堆（Heap）

堆是进程内一片共享的内存区域，由 GC 统一管理。堆上的分配要贵得多：运行时需要在空闲内存里找一个合适的块，之后还要被 GC 扫描、标记、回收，同时可能引入内存碎片和 STW（stop-the-world）的停顿。

代价换来的好处是：堆上变量的生命周期**不受函数作用域限制**，只要还有引用指向它，它就能一直存活。

### 一张对比表

| | 栈（Stack） | 堆（Heap） |
| --- | --- | --- |
| 分配速度 | 极快（移动栈指针） | 较慢（找空闲块 + GC） |
| 生命周期 | 函数内，返回即回收 | 由 GC 决定，可跨函数存活 |
| 是否 GC 管理 | 否 | 是 |
| 典型大小 | 每 goroutine 初始 2KB，可增长 | 进程共享，可很大 |

那么问题来了：**一个变量到底该放栈还是放堆？** 这个决定权不在程序员手里，而在编译器的逃逸分析手里。

## 二、逃逸分析是什么

想先看编译器会怎么判断，可以打开 [Go 逃逸分析实验](/lab/)，对比指针留在当前调用、作为返回值和写入全局变量的结果。

逃逸分析是编译器在**编译期**做的一项静态分析：它追踪一个变量的指针（或引用）是否「逃出」了它所在函数的栈帧。如果编译器能够证明一个变量在函数返回后不会再被访问，就把它放到栈上；否则，就「保守地」把它移到堆上。

这里有一个非常关键、也常常被误解的点：

> **Go 的逃逸分析是保守的。只要编译器无法 100% 确定一个变量不会逃逸，它就会把变量放到堆上。**

所以「看起来不该逃逸却逃逸了」在 Go 里是常态，而不是 bug。反过来也意味着，我们写的代码「形状」会直接影响编译器能否做出更优的栈分配决策。

用一张图直观地看：

```
高地址
┌───────────────────┐
│       堆 Heap      │  ← 逃逸的变量，GC 管理
│   （动态向上增长）   │
├───────────────────┤
│        ...         │
│       栈 Stack     │  ← 不逃逸的变量，返回即回收
│   （动态向下增长）   │
└───────────────────┘
低地址
```

## 三、哪些场景会发生逃逸

下面用几个**最小可复现**的例子，配合编译器的真实输出，把最常见的逃逸场景讲清楚。你可以把代码存成 `main.go`，然后运行：

```bash
go build -gcflags="-m" main.go
```

`-m` 会让编译器打印逃逸分析结果（`-m=2` 会打印更详细的决策依据）。不同 Go 版本输出的措辞略有差异，但核心的 `moves to heap` / `escapes to heap` 是一致的。

### 1. 返回局部变量的指针

这是最经典、也最容易理解的一种逃逸：

```go
package main

type user struct {
    name string
    age  int
}

// newUser 返回一个指针，u 逃逸到堆上
func newUser(name string, age int) *user {
    u := &user{name: name, age: age}
    return u
}

func main() {
    _ = newUser("lin", 18)
}
```

`go build -gcflags="-m"` 会告诉我们：

```
./main.go:9:9: moved to heap: u
```

原因很直观：`u` 是一个局部变量，但 `&user{...}` 的指针被返回给了调用方。函数返回后 `u` 还必须活着，所以它只能住进堆里。

### 2. 变量被 interface 装箱

这是开头那个「反直觉」现象的答案，也是最容易被忽略的逃逸来源：

```go
package main

import "fmt"

func main() {
    x := 42
    fmt.Println(x) // x 逃逸了！
}
```

输出：

```
./main.go:7:13: x escapes to heap
```

为什么会这样？`fmt.Println` 的签名是 `func Println(a ...interface{}) (n int, err error)`。当 `int` 类型的 `x` 被传给一个 `interface{}` 参数时，Go 会发生**装箱（boxing）**：运行时生成一个包含「类型信息 + 数据指针」的 pair。由于编译器无法确定这个 `interface{}` 会被如何使用、数据是否会流到别处，于是保守地让 `x` 逃逸到堆上。

对照一下，内置的 `println(x)` 直接接受具体类型、不经过 interface，`x` 就安安稳稳待在栈上——这就是开头那个现象背后的完整机制。

> 这条知识非常实用：在热路径里，**频繁把具体类型装进 `interface{}`** 是堆分配的一大隐形来源。

### 3. 变量被闭包捕获

闭包会「记住」它捕获的外部变量，这个变量就逃出了原本的函数栈帧：

```go
package main

func counter() func() int {
    count := 0 // 被闭包捕获，逃逸到堆
    return func() int {
        count++
        return count
    }
}

func main() {
    c := counter()
    println(c()) // 1
    println(c()) // 2
}
```

输出：

```
./main.go:4:2: moved to heap: count
```

因为返回的匿名函数 `func() int` 里引用了 `count`，而 `counter` 返回后这个函数还可能被调用，`count` 的生命周期被迫延长到堆上。

### 4. slice 的底层数组

关于 slice 有个很容易混淆的点：**slice 的 header（指针、len、cap）和底层数组是两个不同的东西**。

```go
package main

func makeSlice() []int {
    s := make([]int, 0, 100) // 底层数组在堆上，header 在栈上
    return s
}

func main() {
    s := makeSlice()
    _ = s
}
```

`make` 出来的 slice、map、channel 的内存统一由 runtime 分配、GC 管理，所以底层数组天然在堆上。但 `s` 这个 slice header 本身（3 个 word）是可以栈分配的，返回时只是把这 24 字节的 header 复制一份给调用方。

真正需要留意的是**扩容带来的隐性代价**：

```go
func grow() []int {
    s := make([]int, 0, 4)
    for i := 0; i < 100; i++ {
        s = append(s, i) // 频繁扩容 = 频繁的堆分配与数据拷贝
    }
    return s
}
```

`append` 触发扩容时，runtime 会重新分配一块更大的数组并把旧数据拷贝过去。如果循环里预估不好容量，就会产生大量临时堆分配，这也是性能优化的常见切入点——**能预估容量就 `make` 足容量**。

### 5. 指针被发送到 channel

跨 goroutine 传递指针时，变量会逃逸，因为它的生命周期不再受发送方 goroutine 控制：

```go
package main

func main() {
    ch := make(chan *int, 1)
    x := 10
    ch <- &x // &x 逃逸到堆
    _ = <-ch
}
```

输出：

```
./main.go:7:8: moved to heap: x
```

道理和「返回指针」一样：`&x` 流向了另一个 goroutine，编译器无法保证接收方会在发送方栈帧销毁前用完它，于是把 `x` 放进堆里。相比之下，值类型的 `ch <- x` 只是把值**复制**进 channel，`x` 本身并不逃逸。

## 四、如何观测逃逸与内存分配

除了上面的 `-gcflags="-m"`，日常排查时更常用的是 benchmark 配合 `-benchmem`，它能直接给出每次操作的**分配次数**和**分配字节数**：

```go
package main

import "testing"

type data struct {
    a, b, c, d int
}

// 返回指针：发生逃逸
func returnPointer() *data {
    return &data{a: 1, b: 2, c: 3, d: 4}
}

// 返回值：不逃逸
func returnValue() data {
    return data{a: 1, b: 2, c: 3, d: 4}
}

var sinkP *data

func BenchmarkPointer(b *testing.B) {
    for i := 0; i < b.N; i++ {
        sinkP = returnPointer()
    }
}

var sinkV data

func BenchmarkValue(b *testing.B) {
    for i := 0; i < b.N; i++ {
        sinkV = returnValue()
    }
}
```

运行：

```bash
go test -bench=. -benchmem
```

典型输出（数值随机器和 Go 版本略有波动）：

```
BenchmarkPointer-8   50000000   28.5 ns/op   32 B/op   1 allocs/op
BenchmarkValue-8    1000000000   0.31 ns/op   0 B/op    0 allocs/op
```

同样的 `data` 结构体，只是「返回指针」还是「返回值」这一个差异：前者每次分配 32 字节、多一次堆分配；后者零分配、快了两个数量级。全局变量 `sinkP` / `sinkV` 的作用是「接住」结果，防止编译器把整个调用优化掉。

## 五、优化实践与常见误区

知道了原理，最终要落到怎么写代码上。但先说三个**误区**，它们比技巧更重要：

**误区一：逃逸 = 一定不好。** 错。堆分配有代价，但现代 Go 的 GC 已经相当高效。为了「零逃逸」牺牲代码可读性、或者刻意避免指针，往往是过早优化。

**误区二：`new` 一定在堆、局部变量一定在栈。** 错。放哪取决于逃逸分析，而不是语法。局部变量逃逸了就上堆，`new` 出来的指针不逃逸也可能留在栈上。

**误区三：只要用了指针就逃逸。** 错。函数内部创建、函数内部用完的指针，编译器能证明它不逃逸，照样栈分配。

在此基础上，几条真正值钱的实践建议：

1. **返回值优先，指针仅在必要时用。** 如果调用方不需要修改、也不需要共享，返回值比返回指针更利于栈分配。
2. **热路径里少做 interface 装箱。** 尤其是日志、序列化这类高频路径，避免把大量小对象塞进 `interface{}`。
3. **`make` 时尽量给足容量。** 预判 slice/map 大小，减少扩容带来的临时堆分配与拷贝。
4. **复用对象用 `sync.Pool`。** 对高频创建/销毁的大对象，用 `sync.Pool` 池化，避免反复进出堆。
5. **先测量，再优化。** 动手改之前，先用 `-benchmem` 和 `-gcflags="-m"` 定位真正的分配热点，别凭感觉改。

## 六、总结

逃逸分析是 Go 编译器的一项核心优化，它决定了变量是「栈上速生速死」还是「堆上由 GC 照顾」。理解它，你就理解了：

- 为什么返回指针、interface 装箱、闭包捕获会导致堆分配；
- 为什么 `fmt.Println` 比 `println` 贵；
- 为什么「返回值 vs 返回指针」能在 benchmark 里差出两个数量级。

更重要的是记住那条最底层的判断原则：**Go 的逃逸分析是保守的，编译器证明不了「不逃逸」就放堆上**。所以写代码时，脑子里多想一层「这个变量的生命周期会不会超出当前函数」，往往比死记优化技巧更有用。

当你下次在 `-gcflags="-m"` 的输出里看到 `moves to heap` 时，希望你已经能一眼看懂它背后的故事。
